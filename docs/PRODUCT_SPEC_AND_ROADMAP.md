# Просметчик — техническое задание и дорожная карта продукта

**Статус документа:** основной продуктовый и инженерный контракт.  
**Область:** web desktop, mobile web, React Native, backend, документы, цены, AI/A2A и режим разработчика.  
**Цель продукта:** создать современную chat-first систему для строительной сметы и документации, способную стать альтернативой тяжёлым настольным решениям класса 1С и ГРАНД-Сметы для малого и среднего строительного бизнеса, а затем расширяться до корпоративного контура.

---

## 1. Видение продукта

Просметчик — это не чат, к которому добавили таблицу, и не копия существующей сметной программы. Это единая цифровая строительная контора:

1. Пользователь описывает объект и работу обычным языком.
2. Система формирует карточку задачи, технологическую карту, ресурсы, проверенные цены и смету.
3. В чате показывается один понятный результат — компактная карточка сметы с итогом.
4. Карточка открывает полноценную рабочую область документа: desktop side sheet или mobile bottom sheet.
5. Любая позиция редактируется в один клик, изменения сразу пересчитываются и автоматически сохраняются.
6. Из утверждённой версии создаются КП, договор, приложения, счёт, акт, КС-2, КС-3, М-29 и другие документы.
7. Проект продолжает жить после отправки клиенту: версии, выполнение, оплаты, акты, история цен, документы и переписка связаны между собой.
8. Владелец продукта имеет отдельный режим разработчика: через тот же чат он ставит задачи собственной команде ИИ-разработчиков, которая анализирует, меняет, проверяет и выпускает приложение по контролируемому A2A-контуру.

Главный интерфейс должен оставаться визуально простым, спокойным и понятным человеку без обучения. Сложность хранится в данных, документах, аналитике и агентной системе, а не выставляется пользователю длинной «портянкой».

## 2. Две обязательные пользовательские боли

### 2.1. Боль №1 — ведение смет и документации без постоянной ручной рутины

Сегодня пользователь вынужден разносить одну и ту же информацию по таблицам, Word, мессенджерам, бухгалтерии и архиву. Ошибки возникают между версиями, цены теряют происхождение, а документы расходятся со сметой.

Просметчик должен обеспечить единый поток:

`запрос → объект → технология → ресурсы → цены → смета → утверждение → документы → выполнение → акты → архив`

Обязательные свойства:

- один источник истины для реквизитов, объекта, состава работ и цены;
- версия каждого существенного изменения;
- документы строятся из утверждённой версии, а не из случайного текущего черновика;
- повторное использование подтверждённых цен пользователя и организации;
- явное происхождение цены: личная, организация, прошлый объект, поставщик, официальный источник, исследование или ориентир;
- локальная работа при плохой связи и последующая синхронизация;
- PDF/XLSX и печать выглядят как реальные деловые документы;
- возможность отправить клиенту результат с телефона без лишней навигации.

### 2.2. Боль №2 — развитие и поддержание самого приложения без зависимости от внешней IDE

Владелец должен иметь внутри Просметчика команду ИИ-разработчиков, а не только конечного сметного помощника.

Целевой поток:

`задача владельца в чате → A2A-план → распределение по агентам → изменение в изолированной среде → тесты → review → owner approval → Git → deployment → live-проверка → доказательство релиза`

Обязательные свойства:

- разработка управляется через чат и видимую рабочую область;
- агенты имеют роли, навыки, состояние, задачи и артефакты;
- операции чтения, анализа, изменения кода, Git и deployment разделены разрешениями;
- секреты не попадают в браузер, сообщения или A2A-артефакты;
- изменение не считается готовым по факту коммита: требуется живой проверенный релиз;
- владелец может остановить, отклонить, повторить, продолжить или откатить задачу;
- вся цепочка аудируема по task ID, owner ID, branch, commit SHA, тестам и release SHA.

## 3. Целевые пользователи и роли

### 3.1. Исполнитель / самозанятый

Создаёт смету на объекте, меняет объёмы и цены, показывает итог клиенту, отправляет PDF или ссылку, формирует договор и акт.

### 3.2. Сметчик

Работает с большим количеством позиций, разделами, нормами, коэффициентами, источниками, вариантами и проверками.

### 3.3. Руководитель строительной организации

Управляет сотрудниками, личными и организационными ценами, документами, статусами объектов, выполнением и аналитикой.

### 3.4. Замерщик / прораб

Использует телефон: быстро фиксирует исходные данные, фото, голос, объёмы и корректировки; работает офлайн; передаёт результат в офис.

### 3.5. Заказчик

Получает понятную смету, версии, условия, документы и статус без доступа к внутренней служебной информации.

### 3.6. Владелец продукта

Открывает режим разработчика и управляет командой ИИ-агентов, инфраструктурой, релизами и дальнейшим развитием Просметчика.

## 4. Принципы интерфейса

1. **Один главный результат на сообщение.** Для расчёта — карточка сметы, для документа — карточка документа, для вопроса — короткое уточнение.
2. **Итоговая цена видна сразу.** Название, объект, регион, количество позиций, статус и итог размещаются на первом экране карточки.
3. **Служебные артефакты не формируют длинную ленту.** Технология, ресурсы, кандидаты цен и review сохраняются в состоянии и доступны внутри документа/инспектора.
4. **Открытие без перехода на новую страницу.** Desktop — боковая рабочая область; mobile — нижний sheet.
5. **Редактирование позиции в один клик.** Mobile — bottom sheet позиции; desktop — inline-ячейки и отдельный инспектор при необходимости.
6. **Автосохранение по умолчанию.** Нет обязательной кнопки «Сохранить» после каждого изменения; пользователь видит состояние сохранения.
7. **Прогрессивное раскрытие.** Детали расчёта, технология, допущения, источники, история и служебный trace скрыты до запроса.
8. **Чат остаётся центром управления.** Таблицы и документы открываются поверх текущего контекста, не уничтожая поток.
9. **Одинаковая логика на desktop, mobile web и React Native.** Отличается композиция, а не бизнес-правила.
10. **Действие должно иметь видимый результат.** Никаких декоративных кнопок и вкладок без рабочего поведения.

## 5. Функциональные требования

## 5.1. Чат, проекты и рабочая область

- assistant-ui runtime владеет сообщениями, состоянием запуска, редактированием и ветвлением;
- AG-UI используется для потоковых событий, tool calls, состояния и отмены;
- каждый первый пользовательский запрос создаёт проект/объект и thread;
- thread имеет название, объект, регион, статус, архив и историю;
- sidebar: новый чат, поиск, закреплённые, проекты, архив, настройки;
- right inspector: контекст, артефакты, работа агентов и состояние сервисов;
- mobile sidebar и inspector открываются как sheets;
- восстановление после reload не должно терять сообщения, tool artifacts или активную смету;
- пользователь может продолжить изменение сметы обычным сообщением.

## 5.2. Карточка сметы

Карточка в ленте обязана показывать:

- тип артефакта и статус;
- название сметы;
- объект и регион;
- число позиций;
- текущую версию;
- итоговую цену крупнее остальных элементов;
- одно основное действие «Открыть смету»;
- меню: переименовать, дублировать, версия, удалить.

В обычном режиме до и после карточки не должны автоматически раскрываться большие карточки технологии, ресурсов, цен и review.

## 5.3. Редактор сметы

### Desktop

- открывается справа, не размонтируя чат;
- сохраняет ощущение печатного документа;
- inline-редактирование названия, реквизитов, разделов, позиции, единицы, количества и цены;
- drag-and-drop порядка строк;
- добавление/удаление позиции и раздела;
- undo/redo;
- быстрый доступ к аналитике цены;
- итог пересчитывается детерминированно без вызова модели;
- закрытие возвращает к карточке без потери данных.

### Mobile web / React Native

- смета открывается bottom sheet высотой до 94% экрана;
- строки представлены компактными карточками;
- касание строки открывает bottom sheet редактирования;
- основные поля: название, количество, единица, цена;
- расширенные поля: код, тип ресурса, норма, коэффициент, комментарий, источник;
- клавиатура не должна перекрывать активное поле и итог;
- изменения сохраняются автоматически;
- удаление имеет короткую возможность отмены;
- share использует native share при наличии.

## 5.4. Расчёт и версия

- денежные расчёты выполняются Decimal, а не float;
- позиции группируются по разделам;
- количество × норма × коэффициент × цена формирует прямые затраты;
- накладные, прибыль, скидка и НДС задаются отдельными параметрами;
- каждое утверждение создаёт immutable revision;
- черновик после изменения утверждённой версии получает новый статус;
- история позволяет сравнить версии и восстановить выбранную;
- утверждение блокируется при нулевых критичных ценах, отсутствующих источниках или обязательных реквизитах согласно политике организации.

## 5.5. Технологическая карта и ресурсы

До формирования сметы агент обязан построить технологическую последовательность. Она не обязана занимать место в чате, но входит в данные сметы.

Каждый шаг может содержать:

- название операции;
- описание;
- контроль качества;
- требуемые работы, материалы, машины, оборудование и логистику;
- нормативное или внутреннее основание;
- допущения и риски.

Ресурсная ведомость собирается из технологии и затем сопоставляется с позициями сметы.

## 5.6. Цены и каталог

- личные цены пользователя;
- цены организации;
- подтверждённые цены прошлых смет;
- прайсы поставщиков;
- региональные наблюдения;
- официальные и нормативные источники;
- внешнее исследование с URL/датой/регионом/НДС/доставкой;
- ориентировочная цена только с явным предупреждением.

Для каждой цены хранятся:

- каноническая работа/ресурс;
- регион;
- дата и период актуальности;
- валюта;
- НДС и доставка;
- источник и доказательство;
- confidence;
- старая и новая цена после ручной правки;
- автор подтверждения;
- статус suggested/confirmed/rejected/stale.

## 5.7. Документы

Минимальный комплект:

- коммерческое предложение;
- договор подряда;
- приложение к договору со сметой;
- счёт;
- акт выполненных работ;
- КС-2;
- КС-3;
- М-29;
- дефектная ведомость;
- ведомость материалов;
- спецификация оборудования;
- график работ.

Требования:

- документ создаётся из конкретной версии сметы;
- изменение исходной сметы не меняет уже утверждённый документ без новой версии;
- редактор показывает печатный вид;
- реквизиты подтягиваются из профиля организации;
- missing fields отображаются явно;
- PDF формируется серверно или детерминированно в клиенте без потери кириллицы;
- XLSX содержит редактируемые формулы и структуру разделов;
- доступна печать, download, native share, email и WhatsApp handoff;
- все файлы принадлежат tenant и имеют проверяемый доступ.

## 5.8. Объекты, клиенты и выполнение

- объект объединяет чаты, сметы, документы, файлы, контакты и события;
- клиент может иметь несколько объектов;
- утверждённая смета становится базой исполнения;
- фиксируются проценты/объёмы выполнения, принятые работы, допработы и оплаты;
- акты формируются только по фактически выбранному периоду/объёму;
- dashboard показывает активные объекты, суммы, задолженность, ближайшие действия и проблемные документы.

## 5.9. React Native

Нативное приложение не должно быть отдельным продуктом с другой логикой. Оно использует общие API и схемы домена.

Обязательный первый vertical slice:

1. Вход и выбор рабочего пространства.
2. Список объектов/чатов.
3. Голосовой или текстовый запрос.
4. Получение потокового ответа AG-UI.
5. Карточка сметы.
6. Bottom sheet сметы.
7. Bottom sheet позиции.
8. Автосохранение в локальный store.
9. Outbox при отсутствии сети.
10. Синхронизация после восстановления соединения.
11. Native share PDF/ссылки.
12. Камера и вложения к объекту.

Предпочтительный стек на фазе реализации: React Native + Expo, TypeScript, общий пакет Zod-схем, локальный SQLite/kv adapter без зависимости web-клиента от WASM.

## 5.10. Режим разработчика и A2A

- открывается командой в основном чате;
- публикует Agent Card;
- предоставляет owner-scoped JSON-RPC A2A endpoint;
- показывает реестр агентов и их навыки;
- создаёт task и development-plan artifact;
- поддерживает get/list/cancel;
- в следующих фазах подключает read, code, test, git и deploy adapters;
- каждое повышение разрешения требует owner approval;
- production deployment возможен только после полного release gate;
- режим разработчика не смешивается с клиентским сметным интерфейсом.

Подробный контракт описан в `docs/A2A_DEVELOPER_MODE.md`.

## 6. Архитектура

### 6.1. Web client

- Next.js App Router;
- React;
- assistant-ui;
- AG-UI client/runtime;
- Tailwind CSS;
- IndexedDB local cache;
- deterministic domain calculations;
- sheets, editors and document canvas as normal React components.

### 6.2. Backend

- Next.js Node runtime API;
- PostgreSQL as authoritative server store;
- tenant-scoped repository/services;
- provider gateway: MiMo, OpenAI-compatible, Ollama, Codex CLI and deterministic rules path;
- SSE/AG-UI endpoint;
- document/export services;
- A2A developer endpoint;
- immutable release metadata and health endpoints.

### 6.3. Local-first

Browser:

- IndexedDB stores threads, messages, estimates, revisions, documents, prices, files metadata, outbox and sync state;
- UI writes locally first;
- outbox retries idempotently;
- server assigns canonical revisions;
- conflicts resolve by entity policy, not last-write-wins globally.

React Native:

- отдельный local repository adapter;
- те же domain IDs, revision rules и sync protocol;
- вложения загружаются resumable-процессом.

### 6.4. Agent layer

- AG-UI отвечает за связь пользовательского чата с агентом;
- A2A отвечает за связь с внешними/специализированными агентами и task/artifact lifecycle;
- MCP/инструменты отвечают за конкретные способности и доступ к системам;
- coordinator не подменяет domain engine: арифметика, версии и права остаются детерминированными сервисами.

### 6.5. Deployment

- source of truth — `main`;
- один production runner `prosmet-primary`;
- exact SHA checkout;
- PostgreSQL provision/migration;
- source contract;
- typecheck;
- unit tests;
- production build;
- desktop/mobile Chromium;
- immutable release;
- health/backend/live smoke;
- release evidence artifact;
- автоматический откат или сохранение предыдущего рабочего процесса при failed gate.

## 8. Безопасность и права

- tenant isolation проверяется на API и хранилище;
- server-side secrets никогда не возвращаются в browser payload;
- provider keys шифруются;
- A2A task принадлежит owner/workspace;
- read/propose разрешены отдельно от code/git/deploy;
- высокорисковое действие содержит purpose, scope, expiry и approval record;
- shell и Git выполняются только в изолированной рабочей копии;
- agent не может самостоятельно расширить свои права;
- deployment привязан к commit SHA и проверенному workflow;
- файлы имеют deny-by-default access;
- все важные действия пишутся в audit log;
- удаление пользователя/организации соответствует политике retention и экспорта данных.

## 9. Нефункциональные требования

### Производительность

- первый интерактивный экран: целевой p75 до 2,5 с на нормальном мобильном соединении;
- ввод в composer не блокируется и не теряется во время hydration;
- локальное редактирование позиции: визуальный отклик до 100 мс;
- пересчёт сметы: до 50 мс для типовой сметы и до 300 мс для 10 000 строк;
- autosave не блокирует ввод;
- большие документы используют виртуализацию/постраничную отрисовку.

### Надёжность

- reload восстанавливает последнюю локальную работу;
- отмена streaming run не создаёт ложный успешный ответ;
- повторная доставка sync-команды идемпотентна;
- failed deployment не заменяет рабочий release;
- база мигрируется вперёд контролируемо и имеет проверенный backup/restore.

### Доступность

- клавиатурная навигация;
- видимые focus states;
- корректные dialog/sheet labels;
- touch targets не менее 40–44 px;
- контраст WCAG AA для основных действий;
- reduced motion;
- screen-reader названия цены, позиции и действий.

### Наблюдаемость

- run ID, thread ID, task ID, owner/workspace ID;
- provider/model/latency без утечки prompt secrets;
- sync queue depth;
- document/export errors;
- workflow and release SHA;
- client runtime errors и Web Vitals;
- audit trail high-risk actions.

## 10. Дорожная карта

## P0. Релизная целостность и единый source of truth

**Результат:** `main` автоматически проходит проверки и публикует точный SHA на port 3200.

Gate:

## P1. Компактная смета и рабочая область — текущая фаза

## 11. Definition of Done для любого изменения

Изменение считается готовым только если одновременно выполнены условия:

1. Есть наблюдаемый пользовательский результат.
2. Результат соответствует этому ТЗ или обновляет его отдельным решением.
3. Нет декоративных неработающих элементов.
4. Данные сохраняются и восстанавливаются.
5. Права и tenant boundaries проверены.
6. Source contract проходит.
7. Typecheck проходит.
8. Unit tests проходят.
9. Production build проходит.
10. Desktop Chromium проходит.
11. Mobile Chromium проходит.
12. Для native-функции проходят соответствующие simulator/emulator tests.
13. Изменение опубликовано точным SHA.
14. Live smoke подтверждает релиз.
15. Есть артефакты/логи/скриншоты, достаточные для проверки.

Коммит, отчёт, макет или зелёный unit test без живого результата не являются завершённым релизом.

## 13. Ближайшая последовательность разработки

1. Закрыть P1 и добиться production PASS на main.
2. Убрать остаточный визуальный шум в чате и инспекторе по реальным скриншотам.
3. Довести документы P2 до одного законченного потока: смета → КП → договор → PDF.
