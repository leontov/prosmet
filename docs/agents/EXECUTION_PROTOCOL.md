# Протокол выполнения агентной задачи

Этот протокол обязателен для любого изменения продукта, инфраструктуры, данных или документации.

## 1. Сначала определить наблюдаемый результат

Перед изменением кода агент формулирует:

- кто пользователь;
- какую задачу он выполняет;
- какое поведение изменится;
- где это будет видно;
- какой exact сценарий докажет готовность;
- какие риски и данные нельзя потерять.

Нельзя начинать с абстрактного «улучшить компонент» или «провести рефакторинг». Пример корректной цели:

> На мобильном пользователь открывает карточку сметы, меняет цену в keyboard-safe bottom sheet, закрывает приложение, открывает снова и видит сохранённое значение; затем exact SHA проходит production gate на `https://kolibriai.online`.

## 2. Установить source of truth

До работы проверить:

- текущий `main` SHA;
- последний `MAIN PRODUCTION PASS`;
- live SHA в `/api/health`;
- актуальный пользовательский экран;
- текущие миграции и contracts;
- наличие незавершённых или конфликтующих веток;
- точный production runner и origin.

Старый документ, ветка, canary или скриншот не используется как source of truth без сверки с текущим `main` и production.

## 3. Сделать baseline E2E

Воспроизвести пользовательский путь до изменений. Зафиксировать:

- шаги;
- фактическую ошибку;
- console/network ошибки;
- desktop/mobile геометрию;
- состояние local/server storage;
- SHA и URL.

Тест должен падать по нужной причине, а не из-за случайной задержки, перекрывающего элемента или неверного selector.

## 4. Составить минимальный план вертикального среза

План включает только изменения, необходимые для наблюдаемого результата:

1. доменный контракт;
2. данные/миграция;
3. backend;
4. frontend;
5. offline/sync;
6. tests;
7. deployment/evidence.

Во время UX Premium V1 новые продуктовые модули запрещены. Любое расширение scope должно быть отдельно одобрено владельцем.

## 5. Делегировать через A2A

Координатор создаёт DAG задач и назначает роли. Каждая подзадача содержит:

- цель;
- входные артефакты;
- разрешённые paths/services;
- требуемое permission scope;
- критерии приёмки;
- expected artifacts;
- timeout/retry policy;
- зависимости.

Агент не должен менять соседние области «заодно», если это не нужно для gate.

## 6. Работать в изолированной среде

- отдельная branch/worktree или sandbox;
- точный base SHA;
- чистая установка зависимостей;
- запрещено выполнять тяжёлую сборку на Mac владельца;
- вычисления и браузерные тесты идут на Primary/кластере;
- секреты выдаются краткоживущими ссылками, не копируются в файлы;
- каждый write/deploy фиксируется в audit trail.

## 7. Реализовать от домена к интерфейсу

Предпочтительный порядок:

1. schema/type/domain invariant;
2. deterministic unit tests;
3. persistence/sync;
4. API/tool contract;
5. UI state and interaction;
6. accessibility;
7. E2E;
8. release integration.

UI не должен маскировать отсутствующий backend. Backend не считается готовым без рабочего пользовательского интерфейса.

## 8. Самопроверка агента

До передачи verifier агент обязан:

- просмотреть собственный diff;
- удалить debug-код и временные файлы;
- проверить отсутствие секретов;
- проверить ошибки TypeScript;
- запустить релевантные unit/integration tests;
- проверить keyboard/mobile paths;
- сравнить UI с reference;
- описать оставшиеся риски без преувеличений.

## 9. Независимая проверка

Verifier не использует вывод исполнителя как доказательство. Он проверяет:

- diff и архитектурные границы;
- security/tenancy;
- данные и миграции;
- повторяемость тестов;
- desktop/mobile поведение;
- live-ready deploy path;
- соответствие acceptance criteria.

При расхождении фактов задача возвращается исполнителю с конкретным воспроизводимым defect.

## 10. Commit и PR

Commit должен быть атомарным и описывать пользовательский или инфраструктурный результат.

PR содержит:

- пользовательский результат;
- архитектурные изменения;
- миграции;
- риски;
- tests/evidence;
- rollback;
- точный completion gate.

Запрещено создавать десятки параллельных веток без reducer. По завершении остаётся одна актуальная ветка/PR, остальные закрываются или удаляются.

## 11. Merge и production gate

После merge задача не завершена. Агент обязан:

1. дождаться запуска `Prosmet Main Production`;
2. исправлять каждый красный шаг;
3. не обходить падающую проверку отключением теста;
4. добиться deploy exact SHA;
5. проверить внутренние health/backend endpoints;
6. проверить публичный HTTPS origin;
7. выполнить live desktop/mobile smoke;
8. скачать evidence artifact;
9. сверить live release SHA с `main`;
10. убедиться в `MAIN PRODUCTION PASS`.

## 12. Правило непрерывности

Агент не заканчивает ответ фразой «осталось сделать», если оставшееся действие доступно ему через подключённые инструменты. Он продолжает исправление до зелёного gate.

Допустимая остановка только при внешнем блокере, который технически невозможно устранить имеющимися правами, например:

- DNS находится у неподключённого регистратора;
- истёкший платёжный аккаунт;
- физически недоступный сервер;
- требуемое юридическое подтверждение;
- отсутствующее owner approval для production/secrets.

В этом случае агент обязан:

- доказать точный blocker;
- завершить всё, что не зависит от него;
- дать одно конкретное действие владельцу;
- сохранить автоматическое продолжение после снятия blocker;
- не заявлять о завершении релиза.

## 13. Формат итогового отчёта

Только факты:

```text
Result:
Main SHA:
Production SHA:
URL:
Workflow run:
Gate: PASS/FAILED
Desktop evidence:
Mobile evidence:
Database/migration:
Known blockers:
```

Если gate красный, отчёт не называется релизом.
